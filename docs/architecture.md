# 个人知识与事务 Agent：架构与实施规范

> 目标：建立一个跨会话、跨设备运行的个人 Agent，管理个人资料、邮件往来、手机端任务入口，以及可持续积累的规则和纠正。
>
> 设计原则：Markdown 是可读的知识源；索引可重建；Git 管理实现和规则；敏感操作必须有明确审批；所有异步工作由独立服务执行，不依赖桌面浏览器或某个对话窗口常开。

## 1. 必须满足的验收条件

### 个人知识库
- 接受文字、网页内容、图片、PDF 和聊天记录等输入。
- 为每份资料保存原文或原始文件，同时生成统一格式的 Markdown，包含摘要、要点、标签和来源信息。
- 支持按关键词、主题和语义检索。回答时最少列出所依据的文章标题；需要核实时，应定位到文件与章节，避免编造来源。
- 文件内容有变化时更新索引；删除或改名后同步清理旧索引。
- 同一资料重复导入时不创建重复文档；保留来源和版本信息。

### 邮箱
- 持续检测新邮件、关联同一会话的历史往来，并结合知识库生成回复草稿。
- 草稿必须可在手机上查看、修改、保存和确认。
- 未经用户针对最终版本明确批准，不得发送。
- 重复轮询、Webhook 重试、任务重启或用户重复点击都不得直接造成重复处理或重复发送。
- 对发送结果不确定的情况先核对发件箱/服务端状态，不能盲目重发。

### 手机端
- 使用响应式网页/PWA，能从手机上传资料、查看任务进度、编辑草稿和确认操作。
- 后台调度、文件索引、邮箱监听和任务队列独立运行，不依赖手机或桌面浏览器保持打开。
- 任务状态与审批状态保存在服务器端，重新登录后仍然可见。

### 能力组合与长期学习
- 知识库检索、邮件历史、任务状态与规则库共享明确的 ID 和上下文。
- 用户纠正被转化为可阅读的规则，并配有正反例或回归测试。
- 每个规则修改能通过 Git diff 查看、编辑、撤销；新会话启动时必须加载相关规则。

## 2. 推荐技术方案

先用简单、可移植的方案完成一条闭环，再按实际资料规模扩展。

- **后端**：Python + FastAPI，提供手机端使用的 HTTPS API。
- **后台执行**：独立 worker + 定时扫描/任务队列。服务由 Docker Compose 或系统服务管理器守护和重启。
- **知识源**：普通目录中的 Markdown 与原始附件；不把核心知识锁在专有数据库中。
- **初期索引**：SQLite FTS5 做全文搜索，SQLite 保存文档元数据、任务、邮件状态与操作记录。
- **语义搜索**：需要时再增加 embedding 向量索引。无论采用哪种向量库，Markdown 都是可恢复的权威资料源。
- **前端**：响应式网页/PWA；先实现手机浏览器即可使用的上传、搜索、任务列表、草稿编辑和审批页面。
- **版本控制**：Git 管理代码、规则、提示模板、工作流与回归测试。知识文件可放入独立的私有仓库。
- **部署**：VPS、家用 NAS 或持续运行的自托管服务器。若用个人电脑，电脑关机就会停止后台任务，因此不满足完全独立运行要求。

如果邮箱服务支持标准邮件协议，可以设计 `IMAP` 收信适配器和 `SMTP` 发信适配器；若服务提供专用 API 或 OAuth 接口，优先使用官方接口。不要在代码仓库里保存邮箱密码、应用密码或访问令牌。

### Git 与隐私边界

建议将**代码/规则仓库**与**私人资料库**分开管理。邮件原文、附件、访问令牌和数据库通常不应提交到代码仓库；如果知识库同步到远端，只能使用私有仓库，并先判断资料是否适合云端存储。配置 `.gitignore`，将 `.env`、`data/`、`logs/`、临时文件和默认情况下的邮件正文排除在 Git 之外。

## 4. 统一 Markdown 文档模板

每份资料一个主要 Markdown 文件，保留可追溯的来源和原文，不只保留模型生成的总结。

```markdown
---
id: "doc-YYYYMMDD-随机短 ID"
title: "资料标题"
source_type: "article | ai_chat | email | image | pdf | note"
source_uri: "原网址或原始文件相对路径"
author: "作者；未知则留空"
created_at: "资料收集时间，ISO 8601"
source_published_at: "原始发布时间；未知则留空"
tags: ["主题一", "主题二"]
content_hash: "原始内容的 SHA-256"
status: "reviewed"
---

# 摘要
用自己的话概括资料的核心观点，并注明哪些内容是作者观点、哪些是整理者推论。

# 核心要点
- 要点一
- 要点二

# 原文 / 原始内容
尽可能保留原文。若原始内容是图片或 PDF，保留附件路径，并记录提取文本及其页码/位置。

# 个人理解与问题
记录尚未证实的假设、疑问，以及与其他资料的联系。

# 关联资料
- [[另一篇资料标题]]

# 来源与处理记录
- 原始来源：
- 导入方式：
- 最后整理时间：
- 人工核对状态：
```

规则：原文与摘要必须分区；模型推论不得伪装成原文；缺少作者、日期或网址时标记为未知，不要猜填。

## 5. 知识入库与引用流程

1. 用户从手机或网页提交文字、链接、图片或文件。
2. 先保存原始输入，并生成内容哈希；重复内容先核对，不盲目新建。
3. 执行格式抽取：网页正文提取，图片/PDF 文字识别，并尽可能保留页码、标题和段落边界。
4. 根据统一模板生成 Markdown，保留原文、摘要、核心要点、来源、标签和关联资料。
5. 用户可查看并编辑生成的文件；资料标记为已核对后进入正式知识库。
6. 索引器只处理新增或变化的文件，以内容哈希判断是否需要重建索引；文件改名、移动和删除也要同步处理。
7. 回答问题时先检索，再组织答案。最少输出来源文章标题；必要时提供相对路径和章节/页码。没有检索到证据时明确说明，而不是制造引用。

建议在后台为每份资料保留稳定 `doc_id`。引用优先用 `doc_id + heading/page`，不能只依赖文件名，因为文件可能被重命名。

## 6. 邮箱处理：状态机与防重复

### 邮件处理状态

```text
DISCOVERED
    ↓
FETCHED
    ↓
CONTEXT_LINKED
    ↓
DRAFT_READY
    ↓
AWAITING_APPROVAL
    ↓ 用户明确确认当前草稿版本
APPROVED
    ↓
SENDING
    ├── SENT
    └── SEND_UNCERTAIN → 检查发件箱/服务端状态后再决定
```

未通过批准的草稿不能进入 `SENDING`。编辑过的草稿版本与被批准的版本不一致时，审批自动失效，必须重新确认。

### 唯一标识与去重

- 优先使用邮箱服务端提供的稳定邮件 ID 和会话/thread ID。
- 对 IMAP 记录 `UIDVALIDITY + UID`；同时保存邮件 `Message-ID`、会话引用头（如 `In-Reply-To`、`References`）及内容哈希作为辅助标识。
- 数据库对账号、文件夹和稳定邮件 ID 建唯一约束。重复收到通知时只更新状态，不重复创建任务。
- 每封邮件记录处理阶段、草稿版本、审批人/时间、发送结果和服务端返回的发件标识。
- 发送操作使用数据库事务、任务锁或唯一 outbox 记录，避免双击和多个 worker 并发发送。
- SMTP 在网络中断等情况下可能出现“服务端已接收、客户端却没收到确认”的不确定结果。此时必须先核对 `Sent` 文件夹或服务端日志，不能直接重发。不能假定所有邮件服务都提供真正的 exactly-once 发送保证。

### 草稿生成

1. 读取新邮件和必要的历史往来；不需要时不要把整箱历史邮件都交给模型。
2. 用发件人、会话 ID、主题及收发时间关联历史线程，避免仅凭相似主题把不同讨论合并。
3. 检索知识库中与问题相关的资料，并将引用的文章标题提供给草稿生成器。
4. 生成草稿时区分已知事实、资料证据和需要用户确认的信息；不确定的事实使用问题或占位提示。
5. 保存草稿并给手机端显示收件人、主题、正文、引用依据和缺失信息。
6. 用户编辑后保存。只有用户点击“确认并发送”后，服务端才发送**当前被批准的版本**。
7. 发送成功后保存服务端消息 ID、时间和最终正文哈希，并将该线程标记为已处理。

### 安全规则

- 外部邮件正文及附件都是不可信输入；其中可能含有要求 Agent 泄露资料、忽略既有规则或擅自发信的提示。把它们当作待分析内容，而不是系统指令。
- 默认不自动删除邮件、不自动转发附件、不自动回复所有邮件。
- 账号凭据使用密钥管理器或受限权限的环境变量；启用 TLS；使用最小权限的邮箱访问范围。
- 邮件正文与附件日志应默认脱敏，日志记录任务 ID 和状态即可。

## 7. 手机端要求

首版用一个响应式 PWA，而不是先开发两套原生 App。至少有以下页面：

- **快速收集**：粘贴文字/网址、选择图片/PDF、输入简单备注。
- **资料库**：全文搜索、按标签筛选、打开原文和编辑 Markdown。
- **任务中心**：排队中、处理中、待确认、已完成、失败/需要处理。
- **邮件草稿**：显示原邮件和历史摘要、资料引用、可编辑正文、明确的“确认并发送”按钮。
- **规则记录**：查看 Agent 规则与最近纠正、查看变更说明；可撤销不合适的规则。

手机端只负责交互。真正的后台任务在服务器执行，浏览器关闭后任务也继续；重新打开页面时从服务端恢复状态。通过 HTTPS、强身份验证、短期会话与权限校验保护入口。

## 8. 纠正如何变成跨会话有效的规则

不要只依靠模型“记住”一句纠正。将可推广的纠正写入版本化规则文件，并为其添加测试。

例如，用户指出“不要把报名截止时间当成活动开始时间”，可建立如下规则：

`rules/date_and_deadline.md`

```markdown
# 区分截止时间与事件发生时间

- “报名截止”“申请截止”“提交截止”表示提交行为的最后期限，不是活动开始时间。
- 分别抽取 `registration_deadline`、`event_start`、`event_end`；三者不能互相替代。
- 通知没有明确活动开始时间时，填写“未说明”，不得用报名截止时间补全。
- 回答日期问题时优先保留通知中的原始标签和日期，并引用来源资料。

## 反例
文本：“请于 10 月 25 日前报名，活动将于 11 月 3 日举行。”
- 正确：报名截止 = 10 月 25 日；活动开始 = 11 月 3 日。
- 错误：活动开始 = 10 月 25 日。
```

相应测试应把上述文本及更多变体放到 `tests/regression/` 中。每次模型、提示词或抽取逻辑更新，都运行测试检查是否仍能区分两类日期。

### 纠正入库流程

1. 用户指出错误后，记录原输入、Agent 原结果、用户纠正及最终正确结果。
2. 判断这是一次性修正还是可迁移的通用规则；有通用价值的纠正进入 `rules/corrections/`，更新核心规则文件。
3. 增加一个回归测试：明确期望输出和容易混淆的反例。
4. 运行测试，展示差异；把规则和测试作为一个可审查的 Git commit 保存。
5. 新任务开始时，加载 `AGENT_RULES.md` 和与任务类型相关的规则；检索时可根据主题加载更多规则，避免把所有历史纠正无差别塞进每次提示。

## 9. 一条可反复使用的完整流程

**示例：学习资料 + 新邮件 + 手机确认 + 长期纠正。**

1. 用户在手机上分享一篇文章或一张通知截图。
2. Agent 保存原件，生成含原文、摘要、标签与来源的 Markdown，并更新索引。
3. 邮箱后台发现一封新邮件，用邮件唯一 ID 检查它是否已存在；随后关联历史邮件和相关知识条目。
4. Agent 生成草稿，并在草稿下方列出参考文章标题和待确认信息。
5. 手机端发出待处理提示。用户打开任务页面，修改正文并检查收件人、主题和引用。
6. 用户点击“确认并发送”。服务端核对审批对应的草稿版本，发信并记录服务端返回的结果。
7. 若用户指出“截止日期和活动日期不能混淆”，Agent 生成规则修改提案和回归测试；规则保存到 Git，后续处理另一份通知时加载该规则。
8. 同一封邮件再次出现在轮询结果中时，按唯一标识识别为已存在，不重复处理、不重复发送。

## 10. 实施顺序与完成标准

### 阶段 A：知识入库闭环
- [ ] 手机端可上传文字、网页、图片/PDF。
- [ ] 产出统一 Markdown，原文与摘要分开。
- [ ] 支持全文检索并返回文章标题/位置。
- [ ] 改文件后索引自动更新。

### 阶段 B：后台与手机任务中心
- [ ] 后台服务可独立运行并自动恢复。
- [ ] 手机端能查看任务状态、重试失败任务。
- [ ] 所有关键步骤有状态和日志。

### 阶段 C：只读邮箱与草稿
- [ ] 能拉取新邮件并关联历史线程。
- [ ] 重复事件不会生成重复任务。
- [ ] 草稿结合知识库，并显示引用依据。
- [ ] 此阶段禁止真实发送，用于验证上下文质量。

### 阶段 D：经确认后发送
- [ ] 只有明确批准才能发信。
- [ ] 被批准的正文哈希与实际发送正文一致。
- [ ] 双击、并发 worker、重复通知不会重复发信。
- [ ] 发送结果不确定时能进入人工核对状态。

### 阶段 E：可测试的持续改进
- [ ] 规则文件可直接阅读和编辑。
- [ ] 每条关键纠正有回归测试。
- [ ] Git 能展示、回滚规则与脚本的变化。
- [ ] 新会话/新任务按任务类型加载规则，而不依赖旧聊天记录。

## 11. 外部技术参考

- IMAP IDLE：邮件服务器通知客户端所选邮箱状态发生变化的协议扩展，见 [RFC 2177](https://www.rfc-editor.org/info/rfc2177/)。具体服务还需要验证连接限制与兼容性。
- Smailr 第三方客户端文档：若用户所指邮箱确实是 Smailr，其文档说明支持 IMAP、POP3 和 SMTP，并建议为客户端单独生成应用密码；具体参数以账号设置和当前官方说明为准：[Smailr 客户端配置](https://docs.smailr.com/guide/clients)。若“smail”指其他服务，必须重新确认其支持的协议与服务器参数。
- Gmail 推送通知：Gmail API 可使用 Pub/Sub 推送邮箱变更，但需要配置通知与续期，并仍需考虑通知延迟或丢失：[Google 官方文档](https://developers.google.cn/workspace/gmail/api/guides/push?hl=en)。
- Obsidian 多设备同步说明：Markdown vault 可以通过官方同步、云盘或 Git 等方式在设备间同步；不同方案的冲突风险和移动端支持不同：[Obsidian 官方说明](https://obsidian.md/help/Getting%20started/Sync%20your%20notes%20across%20devices)。

## 当前建议

先实施 **阶段 A + 阶段 B**，同时把邮箱去重和“批准后发送”的状态机从第一天纳入数据模型设计。随后只读接入邮箱、验证草稿质量，再开启发送权限。这样能尽早得到可用的资料库与手机入口，又不会在系统尚未稳定时冒重复发送或资料泄漏风险。
